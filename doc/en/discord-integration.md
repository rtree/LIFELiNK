# Discord Individual Emergency Contact — Research and Preparation (2026-09-26)

## Conclusion and implementation order

The on-device happy path for phone calls and the fixed long-press iBeacon flow (P0-14a/P0-15) was completed on 2026-09-26. The current **MVP main line P0-16 through P0-20** verifies, with a single consenting Discord user, the flow of "invite → identity verification/location-sharing consent → Bot test DM → DM for a real phone event → save the reply to the event." App-to-app Google/Firebase friend linking is a future optional feature. Discord is not a replacement for phone calls.

For this small-scale development effort, the standard official procedure does not mention any Discord-side KYC, pre-screening, or paid API key application for the usual Discord Developer Portal app/Bot creation, Bot token, `identify` OAuth2, or HTTP Interactions access. However, `relationships.read` for a user's complete Discord friend list requires an application to the Social SDK, which is not used here. Review and policy compliance for large-scale rollout is a separate matter. [Official Bot getting-started guide](https://docs.discord.com/developers/quick-start/getting-started) / [OAuth scopes](https://docs.discord.com/developers/topics/oauth2#shared-resources-oauth2-scopes) / [Privileged Intent review](https://docs.discord.com/developers/gateway/getting-started-with-privileged-intent-review)

Assigning Secrets to Cloud Run, granting the runtime service account permission to reference the Secrets, the OAuth callback/signature verification API, and DM testing have not yet been done.

1. Log in to the [Developer Portal](https://discord.com/developers/applications) with your own Discord account and create a single app for LIFELiNK via **New Application / Create App**. A new app comes with a Bot user by default. Note the `Application ID` (the OAuth `client_id`, not secret) and `Public Key` (used for Interactions signature verification, not secret) under **General Information**. You cannot send a "friend request" between a Bot and a user.
2. Issue a Bot token via **Bot → Token → Reset Token**. In principle it is shown only once. **OAuth2 → Client Secret** is used when performing a server-side token exchange via `identify` authorization-code authorization granted by the invited party. This is also secret. The OAuth token and the Bot token are different things; there is no single "Discord API key" as such. **Do not paste the Bot token or Client Secret into this chat, Git, screenshots, or terminal history — enter them directly into the GCP Secret Manager "add version" screen.** If a token is ever leaked, reissue it on the Developer Portal side and replace the Secret version. [Official Bot getting-started guide](https://docs.discord.com/developers/quick-start/getting-started#fetching-your-credentials)
3. Register, under **OAuth2 → Redirects / Redirect URLs**, the exact URL of the HTTPS callback to be implemented later. The candidate is `/v1/discord/oauth/callback` on the existing Cloud Run domain (not yet reachable since it hasn't been implemented). The URL registered here and the `redirect_uri` used at authorization time must match exactly. The counterpart's own Discord ID is obtained from `/users/@me` via the `identify` scope, and is cross-checked against the OAuth `state` and the server-side invitation information. `email`, `connections`, `relationships.read`, and `dm_channels.read` are not needed for this minimal flow. Do not retain the user's OAuth access/refresh token once it is no longer needed after identity verification. [OAuth2 authorization code](https://docs.discord.com/developers/topics/oauth2#authorization-code-grant) / [state](https://docs.discord.com/developers/topics/oauth2#state-and-security)
4. Enable `User Install` under **Installation**; the default scope for User Install is `applications.commands` when needed. This is a candidate path for the recipient to interact with the Bot. Only enable `Guild Install` and the `bot` scope, with minimal permissions, if you also want to test reachability via a shared test server. **User Install or OAuth `identify` alone does not guarantee that the Bot can proactively DM an arbitrary counterpart.** The Bot's DM API call is a separate matter; reachability is confirmed with a real-account test DM and button response. If needed, have the counterpart open the Bot first, and also consider using a common test server, but do not assume the DM is guaranteed. [Installation contexts](https://docs.discord.com/developers/resources/application#installation-context) / [Bot getting-started guide](https://docs.discord.com/developers/quick-start/getting-started#installing-your-app) / [Create DM](https://docs.discord.com/developers/resources/user#create-dm)
5. **General Information → Interactions Endpoint URL** can be **left blank for now**. Set it only after implementing and deploying, on the Cloud Run side, signature verification of `X-Signature-Ed25519` and `X-Signature-Timestamp` (performed against the raw body), a 401 response for invalid signatures, and a PONG (`type: 1`) response to the PING (`type: 1`). The candidate URL is `/v1/discord/interactions` on the same domain (not yet implemented). Registering the URL before this is done will cause Discord's automatic PING verification to fail, and the URL can be unregistered upon a security-verification failure. Button → modal replies are handled via this HTTP endpoint; a persistent Gateway connection or the privileged `MESSAGE_CONTENT` Intent is not required. [Configuring interactions](https://docs.discord.com/developers/interactions/overview#configuring-an-interactions-endpoint-url) / [Response deadline](https://docs.discord.com/developers/interactions/receiving-and-responding#interaction-callback)

## Expected behavior and constraints after implementation

- The caller is authenticated via Firebase and issues a time-limited, single-use invitation. The recipient personally authorizes `identify` and **separately** gives explicit consent to emergency DMs and prefecture-level location sharing. This does not import the recipient's entire Discord friend list, nor does the Bot become the user's friend.
- Cloud Run uses the Bot token to call `POST /users/@me/channels` with `recipient_id`, then sends the message to the obtained channel ID. This is not a DM sent on the user's behalf using the user's OAuth token. Sending can fail due to the recipient's settings, blocking, lack of a shared server, or rate limits (e.g. `50007`, `50278`, `40003`, HTTP 429). HTTP send success is distinct from being read, from push notification delivery, and from an actual rescue occurring. The phone call remains the primary channel; a failed DM does not halt the process. [Create DM](https://docs.discord.com/developers/resources/user#create-dm) / [Error codes](https://docs.discord.com/developers/topics/opcodes-and-status-codes#json-json-error-codes)
- A Discord reply is cross-checked, using the `user.id` of the signature-verified button/modal Interaction, against the event's authorized recipient, deduplicated idempotently by `interaction.id`, and saved to Firestore. Initially this is treated as reference information only and is not automatically injected into the call's AI. The initial response to an HTTP Interaction must occur within 3 seconds, and the follow-up token is valid for 15 minutes. Receiving all free-text DMs would require a separate persistent Gateway connection. [Responding to interactions](https://docs.discord.com/developers/interactions/receiving-and-responding)
- Demo Discord DMs must not include GPS coordinates, precise map links, street-level addresses, audio files, or call transcripts. Information minimization, a recipient revocation path, delivery status, and duplicate-resend prevention must be confirmed at implementation time.
